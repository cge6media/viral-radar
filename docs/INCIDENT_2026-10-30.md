Investigated and repaired from the cloud workspace with the GitHub CLI (REST API) on 2026-10-30, 16:08–17:30 UTC.
No personal machine, no paid service. Recovery checkpoint before any change: branch `v4-stable` (= `1ef4b60`, the
4.0.2 deployment with the data of 15:04 UTC).

## Root causes (established from logs/API, then reproduced offline)

1. **A quadratic clustering step.** `buildClusters` merged topic seeds in a `while (merged)` loop that re-tokenised
   every member of every topic pair and restarted after each merge, then attached every video to topics by
   recomputing each topic's token set per video (`O(videos × topics × members)`), and compared every microtrend
   pair for overlap. All three scale with the 7-day window, which was one day old at release and full by 10-30.
   Offline profile on the 15:04 data: the cluster stage alone ran **> 12 minutes** (the whole run > 20 min);
   with precomputed token sets and inverted indexes it runs in **7.7 s** and the pipeline in ~2.5 min offline
   (≈ 60 s of that is the sandbox's blocked network timing out).
2. **Stale checkout after a queued start.** Job-level concurrency starts the next queued collect job the moment
   the previous one completes; its checkout can miss the push made seconds earlier, so the freshness gate saw old
   data, a full pipeline ran, and the push was rejected; the simple `git pull --rebase` could not resolve the
   regenerated snapshot files and the run failed. Both causes compound: long runs mean more queued jobs.
3. **Queued runs superseded.** With four staggered schedules plus the keeper chain and 20-minute runs, most
   triggers found a job running; GitHub keeps one pending job per concurrency group and cancels the older pending
   one. These cancellations are not failures and never touched the data, but they fill the Actions page (and may
   be emailed depending on the account's notification setting).

Not causes (checked): YouTube quota (max 7,599 of 9,000 units on 10-29; 90/90 searches only at the end of the
Pacific day, as designed), permissions (unchanged, `contents: write`), secrets (the key worked on every successful
run), sources (4/5 OK on every run; TikTok disabled by design), the release gate (`gate: true` on every data commit),
invalid data (15/16 quality checks; the one warning is informational).

## Fixes

- `pipeline/src/intel/cluster.ts`: topic merge, topic attachment, microtrend merge and corroboration rewritten with
  token sets computed once and inverted indexes (candidate pairs only among clusters sharing a token or member).
  Same clustering rules; test suite unchanged and green (56 tests).
- `.github/workflows/collect.yml` (+ generated `collect-b/c/d.yml`): a **Sync to the tip of main** step after
  checkout (15 s pause, `git fetch` + `reset --hard origin/main`) so the gate reads the true latest data;
  **Commit data** replays the run's commit on a moved `main` instead of failing — up to five attempts with
  `git rebase -X theirs` where append-only NDJSON logs merge by union and regenerated JSON files take the replayed
  run's version whole (`.gitattributes` + a `takeours` merge driver) — a conflict that survives that is a genuine
  failure; job timeout 20 → 30 min as headroom; the keeper also skips when the published data is < 20 min old.
- Growth controls so the next slowdown does not arrive in two weeks: observation files older than 9 days are
  compacted to the last state per id (metric history is only read for 8 days), score history retention 14 → 7 days,
  score records only for shipped trends.
- Monitoring: per-stage timings in every run's health record and `health.json → stages`; workflow-level health
  from the Actions export (`health.json → workflow`: last failed run, last cancelled run, consecutive failures,
  24-h success/failure/cancelled counts), shown on the Radar health tab with cancelled explained as "timed out or
  superseded, not a failure".

## Notifications

GitHub sends the "Run failed" email to the actor of the run; for scheduled runs that is the account that last
committed the workflow file (the owner). There is no per-repository switch for Actions emails — the per-user
setting under Settings → Notifications → Actions ("Only notify for failed workflows", email on/off) is global, so
it was left untouched. The flood stops because the failures stop; a Gmail filter is the stop-gap for anything that
still arrives (see the report).
